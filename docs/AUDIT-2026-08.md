# Plugin audit, 2026-08-04

A whole-plugin read after a night of piecemeal fixes produced several wrong
diagnoses. The point of this document is to hold the shape of the system in one
place so the next question can be answered from understanding rather than from
grepping, and to rank the optimisation paths by evidence rather than by which
file happened to be open.

**Measured** means a number from a profiler log or a live query this session.
**Inferred** means read from code and not yet observed. They are labelled
throughout; do not act on an inferred number without measuring it first.

---

## 1. What the pieces are

27 scripts, ~13,000 lines. Two files hold 50% of it:

    highpoly_mapcontext.gd   3793   the borrowed level: terrain, props, backdrop,
                                    water, roads, cells, streaming
    highpoly_toggle.gd       2745   EditorPlugin + the whole dock UI
    highpoly_sync.gd          652   background model download/diff/queue
    highpoly_lib.gd           593   the placed-object overlay (proxy <-> our mesh)
    highpoly_store.gd         522   where downloaded models live, on-disk index
    highpoly_lighting.gd      443   sun/sky/GI rig + the map's own light entities
    highpoly_scatter.gd       432   grass/shrub scatter around the camera
    ... 20 more, each one concern

Roughly, the plugin is **four independent overlays** over the user's scene, all
`owner = null` so none of them can ever be saved:

    _MAP_CONTEXT     terrain + props + backdrop + water   (mapcontext)
    _HIPOLY_PREVIEW  per placed object, our mesh          (lib)
    _GAME_LIGHTING   sun/sky/env      _MAP_LIGHTS  lights (lighting)
    _MAP_FX / _GAMEMODE / _COLLISION_VIS                  (fx / gamemode / collision)

Detail Mode governs the first two; everything else is its own toggle.

## 2. The half-second tick — the thing to understand first

`highpoly_toggle.gd` runs ONE 0.5 s timer, and almost every recurring cost in
the plugin hangs off it. In call order:

| call | cost scales with | measured / inferred |
|---|---|---|
| `_check_scene_change()` | O(1), early-returns when root unchanged | measured cheap |
| `_lighting_guard()` | O(1), string check + dict lookup | measured cheap |
| `mapctx.tick()` -> `_apply_radius` | cells + backdrop entries | **152 + 340** on Dumbo (measured) |
| gamemode self-heal | O(1) node lookup, only when a variant is picked | cheap |
| `LightingScript.tick_lights()` | **every Light3D under `_MAP_LIGHTS`** | **up to 11,640** (measured count) |
| `ShapeViz.tick()` | tracked collision nodes, **every 8th tick** | 0 in an empty scene |
| `HighpolyCollision.refresh_transforms()` | tracked nodes, only when collisions on | scene-dependent |

Two independent sub-cadences hide in here and are worth knowing by heart:

* `ShapeViz.TOPUP_EVERY = 8` -> **fires every 4.0 s**
* `highpoly_previews` has its own 2.0 s timer, separate from this one

There is no 3-second timer anywhere in the plugin. A user reporting "hitching
every ~3 seconds" is most likely describing the 4.0 s ShapeViz cadence; that is
the only interval close to it.

## 3. Optimisation paths, ranked

### 3.0 What the engine already does that we reimplemented — RESEARCHED

Checked our approaches against Godot's own guidance rather than assuming ours
were optimal. Two of the three came back well, one did not.

**Light culling: we already use the engine feature — CORRECTION.** An earlier
revision of this document claimed we were reimplementing `distance_fade` by
hand. That was wrong, and it was wrong because `tick_lights` was read without
reading `set_map_lights`. Distance fade IS enabled on every light at build time
(begin 90 m, length 40 m). What actually exists is BOTH: GPU fade, plus a
coarser GDScript visibility pass that keeps distant lights out of the clustered
budget entirely. The second is worth keeping — it just was not worth repeating
for a camera that has not moved.

The verified failure was the cadence, not the technique: the pass ran on every
half-second tick over all 11,640 lights whether or not anything had changed.

Two things that came with it:
* Forward+ allows many lights but caps **512 clustered elements in view**
  (omni + spot + decal + reflection probe combined). Dumbo builds 11,640 lights,
  so we are far past that ceiling whenever a dense area is on screen — meaning
  the current behaviour is not just slow, it is over budget by construction.
  Capping what gets BUILT is therefore correctness as well as speed.
* Known caveat: distance fade has had bugs where shadow updates continue for
  faded lights (godot#88085, #118022). Our map lights should be shadow-less, so
  this should not bite, but verify rather than assume.

**MultiMesh cells: our design is the documented workaround, not a mistake.**
Godot 4 has NO per-instance frustum culling and NO per-instance LOD inside a
MultiMesh; the open proposal for it (godot-proposals#10669) estimates a
50-200% win if it ever lands. Until then the recommended approach is exactly
what we do — split into spatial patches and accept the batching loss. This
independently explains the measured cell-size result in 3.4: there is no
setting that avoids the trade, only a place to sit on the curve.

**Backdrop: prefer a texture array over an atlas.** Both collapse many
materials into one, but a `Texture2DArray` keeps each image separate with its
own mipmap chain, whereas an atlas needs manual slicing in the fragment shader
and hand-managed padding. Since backdrop cards are mostly uniform small sizes,
an array indexed per instance avoids the UV rewrite and the seam/bleed risk that
made me rate the atlas as risky. It also sidesteps the ~31% of cards whose UVs
tile outside 0-1, which an atlas cannot represent at all — a tiling UV is fine
against an array layer. **This supersedes the atlas plan in 3.3.**

### 3.1 `tick_lights` is O(all lights) every half second — INFERRED, high value

`highpoly_lighting.gd:435` walks every child of `_MAP_LIGHTS` doing a
`distance_squared_to` and a `visible` assignment. There is **no cap** on how
many lights get built: `set_map_lights` creates one `Light3D` per row of
`lights.json`, and Dumbo's has **11,640**.

So with Map Lights on, ~11,640 iterations run twice a second forever, whether or
not the camera moved. `visible` early-outs when unchanged, so the cost is the
loop itself, but the loop is the point.

Fixes, cheapest first:
1. **Skip when the camera hasn't moved.** The dock already has the camera; a
   position compare turns the steady-state cost to zero.
2. **Bucket by cell.** Same trick the props use — only test lights in nearby
   cells instead of all of them.
3. **Cap what gets built.** Nothing needs 11,640 live `Light3D` nodes; build the
   nearest N and rebuild on cell crossings.

Measure before and after with a stationary profiler recording; if this is the
hitch, it will show as a regular dip at 2 Hz.

### 3.2 `_on_node_added` fires for every node the plugin itself creates — INFERRED

`get_tree().node_added` is connected for the plugin's whole lifetime and is only
disconnected in `_exit_tree`. Every node added anywhere in the tree runs:

    node is Node3D -> name checks -> get_edited_scene_root()
      -> root.is_ancestor_of(node)      walks UP to the root
      -> HighpolyLib.in_overlay(node)   walks UP again
      -> match_key_public(node)         string work

A map-context build adds **~11,600 nodes**, so the build pays ~11,600 ancestor
walks purely to discover that its own nodes are its own. Disconnecting the
handler for the duration of a build (and reconnecting after) is a contained
change and should take a visible bite out of build time — which users describe
as "building the scene takes forever".

### 3.3 The backdrop is the worst draw-call-per-triangle in the scene — MEASURED

    backdrop   6,618 surfaces   0.1M triangles   ~17% of a frame
    49,966 primitives across 155 files, one material AND one image per primitive

Nothing to merge (verified: a material-merge pass found zero groupable surfaces)
and ~31% of the cards tile their UVs (range -17.5 to +21.5), so they cannot be
atlased either. A partial atlas of the 69% that stay inside 0-1 would take a
typical file from ~324 surfaces to ~100 — about **3x**, not the 50x the raw
material count suggests. Real work, real seam risk, and it is now the largest
single line item that has no cheap fix.

### 3.4 Cell size is a dead end — MEASURED, do not revisit

Averaged over 24 camera positions, moving the prop grid from 64 m to 96/128/192 m
changes draw calls by 2-3%. Only 256 m helps (-26%) and it costs 70% more
triangles. A single-camera sample suggested a 2x win; the average did not. This
was measured and rejected.

### 3.5 Section rebuild on every layer toggle — KNOWN, unfixed

`mapcontext.apply()` opens with `_clear(root)`, so flipping ANY map-context
checkbox tears down all ~11,600 nodes and rebuilds. There are fast paths
(`set_context_shown`, `set_backdrop_shown`, `set_water_shown`, `reskin`) that
avoid it, but Extended Terrain has none, so that one toggle always pays a full
rebuild. Tracked as #38.

## 4. Correctness issues found while reading

* **`_on_node_added`'s comment is now stale.** It says "No mode gate: dropping an
  asset in Low-Poly must still fetch and skin it." Since Low-Poly became
  proxy-only, that path shows the proxy and returns — harmless, but the comment
  documents behaviour that no longer exists, and the work is now wasted.

* **`highpoly_variants.gd` forces `Tier.HIGH`** when cycling a variant, so
  double-clicking in Low-Poly swaps our geometry in against the selected mode —
  and with Low-Poly downloading nothing, the model may not be present, producing
  "variant failed to load". Deliberate per-object override or bug, needs a call.

* **`SHADOW_MIN_EXTENT` is not the shared boundary its comment claimed.** The
  HLOD tiers (`_set_mmi_lod`) and the placed-object cull (`highpoly_placedcull`)
  each carry their own literal `12.0`. They happen to match; nothing enforces it.
  Corrected in the comment 2026-08-04.

* **Intent that lives in a variable gets overwritten.** Backdrop and terrain had
  `cast_shadow = OFF` set at build time, and BOTH the shadow toggle and the cell
  updater re-derived casting from mesh extent and switched them back on — 6,627
  skyline surfaces casting again, 26,508 draw calls. Fixed by moving the intent
  onto the node as a `no_shadow` meta that every later pass must honour. **This
  is the general lesson: if a later pass re-derives a value, storing the decision
  in that value cannot hold.**

## 5. Where the frame actually goes (Dumbo, worst frame, everything on)

Measured across the session, same flight path:

    155,468 calls  24 fps median   4 lowest    session start
     47,783         42            10           backdrop stops casting
     39,166         50            11           shadow threshold 20 m
     18,859         49            19           + prepass restored, LOD 0.2/0.4

Final split:

    props, geometry   5,057 calls
    backdrop          6,618 calls    <- largest, no cheap fix (3.3)
    props, shadows    2,016 calls
    unattributed      4,808 calls    <- profiler cannot see it; not understood

The unattributed block moved with the depth prepass and did NOT move with the
backdrop, which rules out "per-surface work the profiler under-counts". It is
the largest unexplained item and the honest next investigation.

**Do not disable the depth prepass to chase it.** SSAO and SDFGI occlusion read
that buffer; with it off they resolve to fully occluded and interiors and streets
go pitch black. It is invisible while game lighting is off, which is how it
passed a performance test before being caught.

## 6. Applied 2026-08-04, with the evidence

Three changes, each verified headless before being written up rather than after.

### 6.1 The light cull skips a stationary camera

`tick_lights` walked all 11,640 lights twice a second regardless of movement.
It now early-outs unless the camera moved more than 1 m, with an explicit
`invalidate_light_cull()` for the two cases that change the answer without
moving: rebuilding the light set, and moving the Range slider.

Measured on a 4,000-light stand-in (Dumbo is ~2.9x that):

    first pass                       1089 us   301 of 4000 lit
    stationary repeat                 189 us   loop skipped
    after moving 5 m                           corrected
    range 150 -> 10 m, camera still            31 lit, corrected

The "loop skipped" line is proven, not assumed: a light was deliberately set to
the wrong visibility before the repeat tick and was still wrong after it.

### 6.2 The gizmo tidy-up is spread instead of spiked

`ShapeViz.tick()` did nothing for seven ticks then walked EVERY tracked node on
the eighth — a spike every 4.0 s, the only interval in the plugin close to the
"hitching every ~3 seconds" reports. It now sweeps `SLICE = 192` nodes per tick
with a carried cursor.

    cursor over 8 ticks: 0->192, 192->384, ... 960->152, 152->344
    full sweep of 1000 nodes: 6 ticks = 3.0 s, none of it in one frame
    every tick advanced by <= SLICE: true
    a node dying mid-sweep: pruned, cursor reset, no crash

Note the clearing itself CANNOT be tested headless — gizmos do not exist without
an editor, so `get_gizmos()` is always empty there. Only the traversal is
covered by that test; the clearing needs an editor session to confirm.

### 6.3 The build no longer notifies itself about its own nodes

`_on_node_added` is connected to the tree-wide signal, so each of the ~11,600
nodes a map-context build adds paid `get_edited_scene_root()`, an
`is_ancestor_of` walk up to the root, and a second walk up in `in_overlay()` —
to conclude that our node is ours. It now returns immediately while
`mapctx.is_build_done()` is false. Nothing is missed: everything a build creates
is overlay geometry, which `in_overlay()` rejected anyway.

Not separately measured; the saving is arithmetic (11,600 walks that no longer
happen), and it should show up as shorter builds rather than smoother frames.

## 7. Not started, and why

**Backdrop texture array (3.0 / 3.3).** Scoped and understood — decode ~50,000
images, build per-file `Texture2DArray`s, index per instance, drop the per-card
materials — but it is hours of pipeline work, requires republishing mapdata for
22 maps, and lands as a visible change to every horizon with no one awake to
eyeball it. The failure mode (wrong layer index, mis-sampled card) is silent and
map-wide. Worth doing deliberately, not unsupervised.
